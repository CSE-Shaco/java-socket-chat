# 아키텍처와 상태

## 구성

하나의 Java 21 애플리케이션 안에 클라이언트, 서버, 공유 프로토콜을 둡니다. 외부 런타임 라이브러리 없이 표준 TCP 소켓과 Java 직렬화를 사용합니다.

- `client.core.ChatClient`는 Swing을 모르는 통신 세션입니다. 명령을 비동기로 보내고 서버 이벤트를 전달합니다.
- `client.attachment.AttachmentService`는 첨부 파일의 크기 검증·읽기·저장과 제한된 이미지 디코딩·미리보기 크기 조정을 담당합니다. 통신이나 Swing 컴포넌트를 알지 않습니다.
- `client.gui.ChatApplicationWindow`는 하나의 프레임과 통신 세션을 소유합니다. `LobbyPanel`, `MatchingPanel`, `ChatPanel`이 각각 로비·매칭 대기·채팅 화면을 맡으며, Swing 변경은 EDT에서 처리합니다. 화면 전환이 메시지 소켓의 수명을 바꾸지 않습니다.
- `server`는 메시지·파일·방 목록 포트의 소켓 수락, 세션 명령 처리, 방 및 매칭 상태, 세션별 출력 큐를 담당합니다.
- `shared.protocol`은 클라이언트와 서버가 함께 쓰는 요청·응답 타입 및 WireIO 직렬화 경계입니다.

## 연결 흐름

1. 클라이언트가 메시지 포트에 연결하고 `Hello(User)`를 보냅니다.
2. 서버는 수용 한도와 입력을 확인하고 연결을 세션에 결합한 뒤 `Welcome(sessionId, token, user)`를 응답합니다.
3. 클라이언트가 별도 파일 포트에 연결해 `BindFile(token)`을 보냅니다. 서버의 `FileReady`를 받은 뒤 파일 채널을 사용합니다.
4. 메시지 연결은 로비·매칭 대기·채팅방 이동 동안 유지됩니다. 방 목록 조회는 별도의 짧은 연결을 사용합니다.
5. 창을 닫거나 연결이 끊기면 세션, 대기열, 방 참여와 파일 연결을 정리합니다.

## 상태 모델

한 메시지 세션은 한 시점에 다음 상태 중 하나에 있습니다.

| 현재 상태 | 명령 또는 사건 | 다음 상태 |
| --- | --- | --- |
| `LOBBY` | `CreateRoom`, `JoinRoom` | `IN_ROOM` |
| `LOBBY` | `StartRandom`, 대기 상대 없음 | `WAITING` |
| `LOBBY`와 상대의 `WAITING` | `StartRandom`, 매칭 성공 | 두 세션 모두 `IN_ROOM` |
| `WAITING` | `CancelRandom` | `LOBBY` |
| `IN_ROOM` | `LeaveRoom` | `LOBBY` |
| 랜덤 방의 `IN_ROOM` | 상대 퇴장 또는 연결 종료 | `WAITING`, 적합한 상대가 있으면 새 방의 `IN_ROOM` |
| 모든 활성 상태 | 연결 종료 | `CLOSED` |

방 ID, 현재 참여 상태, 발신자 이름은 요청 본문을 신뢰하지 않고 서버 세션에서 결정합니다. 상태 변경은 서비스가 직렬화해 적용하고, 소켓 쓰기는 그 상태 락 밖의 세션 송신 작업이 담당합니다. 방 목록에는 공개 방만 표시합니다.

## 랜덤 채팅 자동 재매칭

랜덤 방에서 한 사용자가 나가거나 연결을 종료하면 기존 방을 즉시 제거하고, 남은 사용자를 대기열에 등록합니다. 먼저 `Waiting`을 보내고, 적합한 대기자가 있으면 새 방에 매칭해 `MatchFound`를 보냅니다. 직접 나간 사용자는 로비로 돌아가며, 대기 취소도 가능합니다. 공개 방의 남은 참가자는 기존 방에 계속 머뭅니다.

각 세션은 마지막으로 매칭된 상대 세션 ID를 기억합니다. 어느 한쪽이라도 상대를 직전 상대로 기억하면 다시 매칭하지 않습니다. 대기 취소 후 다시 시작해도 기록은 유지하며, 다른 상대와 매칭됐을 때만 갱신합니다. 대기열은 먼저 들어온 적합한 상대를 선택하고, 제외된 후보는 순서를 유지한 채 남겨둡니다. 직전 상대만 남아 있으면 계속 기다립니다. 이 기록은 현재 연결 세션에 한정하며, 재접속한 사람의 신원을 추적하지는 않습니다.

## 랜덤 매칭 후 중복 방 생성 방지

이전 구현은 매칭으로 방을 만든 뒤 대기 창의 소켓을 닫고, 채팅 창에서 새 연결과 입장 요청을 만들었습니다. 기존 세션 정리와 새 입장이 겹치면 익명 방이 삭제되고 같은 ID의 일반 방이 다시 만들어질 수 있었습니다.

현재 매칭은 하나의 상태 변경 안에서 방을 만들고 두 세션을 바로 참가자로 등록합니다. `MatchFound`를 받은 클라이언트는 화면만 전환하며 재접속하거나 `JoinRoom`을 보내지 않습니다. `JoinRoom`은 존재하는 공개 방에만 입장할 수 있고 방을 생성하지 않습니다. 매칭 직후 추가 입장 요청과 반복 매칭 요청에도 방 수가 하나로 유지되는지 서비스·실소켓·클라이언트 통합 테스트로 검증합니다.

## 동시성과 종료

각 세션의 출력은 유한 용량의 큐를 거쳐 순서를 유지합니다. 서비스 상태 변경 중 수신자 소켓에 직접 쓰지 않습니다. 큐가 수용 한도를 넘거나 연결이 실패하면 해당 세션을 닫고 서비스 상태에서 제거합니다. 서버 시작은 세 채널의 포트를 모두 연 뒤 완료되며, 종료 시 수락 소켓과 세션 작업을 닫습니다.

세부 메시지와 역직렬화 제한은 [통신 규약](protocol.md), 포트·실행 설정은 [실행 안내](runbook.md)를 참고하세요.
